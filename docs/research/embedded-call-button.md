# An Intercom-style call button, limited to one domain

Written 2026-10-17. All pages below were read 2026-10-17. Written before anything was tried in a browser. Chromium 141 on a local rig has since settled several of the "not checked" lines below (marked **Seen**; the table is in [call-panel-in-browsers.md](call-panel-in-browsers.md)). Still not tried: any phone, Safari, Firefox, the live Portal and core. This is research, not a decision. It builds on [call-link-domain-limit.md](call-link-domain-limit.md) (plain-link `Referer` check, registrable-domain matching, the Public Suffix List, the CORS option); that is not repeated here.

## What is new

Today the Business pastes an `<a target="_blank">` to the Portal. Petter wants a loader snippet that puts a launcher button on every page and opens the voice line inside the page. The page the visitor talks in is the core's call page, so it gets framed (or popped up) from the Business's site, which changes which checks are possible.

## 1. Precedent: how others install and restrict

**Intercom install.** Two parts: a `window.intercomSettings` object holding `app_id`, then a loader that creates a `<script>` element pointing at `https://widget.intercom.io/widget/<APP_ID>` and inserts it. Paste it "before the `</body>` tag on every page you want the Messenger to appear". [Intercom install](https://www.intercom.com/help/en/articles/168-install-intercom-for-users-on-your-website), read 2026-10-17. The article says nothing about Content Security Policy.

**Intercom restriction.** Yes: Messenger settings, General, "Keep your Messenger secure", a list of trusted domains the Messenger "can be seen on". Blank means any domain. Comma-separated; a leading `*` covers subdomains (one wildcard, first character only); enter the full name such as `www.intercom.com`; `localhost` is not supported, `127.0.0.1` and `0.0.0.0` are. [Intercom trusted domains](https://www.intercom.com/help/en/articles/4418-list-trusted-domains-you-use-with-intercom), read 2026-10-17. How it is checked (Referer, parent page, script request) is **not documented there**.

| Vendor | What it restricts | Wildcards | How it checks |
|---|---|---|---|
| Zendesk Web Widget ([allowlist](https://support.zendesk.com/hc/en-us/articles/10212540848538-Using-an-allowlist-to-manage-where-the-Web-Widget-appears), read 2026-10-17) | Allowlist of domains where the widget can be shown; the snippet can still be pasted elsewhere but "stops the code snippet from functioning" | `*.yourdomain.com`; whether it covers the bare apex: not said | not documented |
| Crisp ([domain lock](https://help.crisp.chat/en/article/why-am-i-getting-an-invalid-chatbox-code-or-invalid-website-error-8j93zr), read 2026-10-17) | "Lock the chatbox to website domain (and sub-domains)"; other domains cannot load the same chatbox | subdomains included by the setting's name; which ones: not said | not documented |
| Vimeo embeds ([domain-level privacy](https://help.vimeo.com/hc/en-us/articles/30030693052305-How-do-I-set-up-domain-level-privacy), read 2026-10-17) | Up to 50 allowed domains per video; unlisted sites "receive an error message" when they embed | not said | not documented; direct links not addressed |

Tawk.to, Drift, Calendly, Stripe: **not checked** (a search found no tawk.to page; the others not tried). Gleap's page returned "Not found". Pattern: three vendors say what is restricted and none says how. All three work on their own server when the widget loads, so each is the kind of browser-header deterrent the earlier note describes. That is a reading of the pages, not something any of them states.

## 2. Two ways to open the call: what the call page can learn

| | (a) iframe panel | (b) popup (`window.open`) |
|---|---|---|
| `Referer` on the request | The iframe's `referrerpolicy` attribute defaults to `strict-origin-when-cross-origin`: "only send the origin when the protocol security level stays the same (HTTPS→HTTPS)" ([MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), read 2026-10-17). That the embedding page is the source of the `Referer` is not stated in a page I read: **not checked**. Our loader creates the iframe, so it can set `referrerpolicy` on it; whether that beats a page-wide `no-referrer` from the Business: **not checked** | Same as a link click. The spec's window open steps pass `referrerPolicy` as empty unless `noreferrer` is set, which also forces `noopener`. [HTML window open steps](https://html.spec.whatwg.org/multipage/nav-history-apis.html), read 2026-10-17 |
| `document.referrer` in the page | Cross-origin: "the `origin` of the parent's `Window.location` by default" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Document/referrer), read 2026-10-17) | MDN does not cover this case; **not checked** |
| `Sec-Fetch-Dest` | `iframe` | `document` (a top-level navigation) |
| `Sec-Fetch-Site` | `cross-site` from another registrable domain; computed over the whole redirect chain, so our 302 does not hide it ([Fetch Metadata §4.1](https://w3c.github.io/webappsec-fetch-metadata/), read 2026-10-17) | `cross-site` when a script opens it; `none` only for browser-UI navigations (typed, bookmark) ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site), read 2026-10-17) |
| Parent identity in script | `location.ancestorOrigins` lists ancestor origins; `no-referrer` on the iframe replaces the entry with `"null"` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Location/ancestorOrigins), read 2026-10-17). Or a `postMessage` handshake: `event.origin` is set by the browser ([MDN postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage), read 2026-10-17) | `window.opener` only without `noopener`; MDN: with `noopener` the new window "will not have access to the originating window" ([MDN open](https://developer.mozilla.org/en-US/docs/Web/API/Window/open), read 2026-10-17). Cross-origin `opener` access beyond `postMessage`: **not checked** |
| Needs a tap | no | yes: popups "must be opened in direct response to user input" (MDN open); the launcher click qualifies |

Browser versions (MDN browser-compat-data, [repo](https://github.com/mdn/browser-compat-data), read 2026-10-17; iOS versions mirror Safari unless noted): `Sec-Fetch-Dest` and `Sec-Fetch-Site` Chrome 80/76, Firefox 90, **Safari 16.4**. `Location.ancestorOrigins` Chrome 20, Safari 6, **Firefox 148**. So an iPhone on iOS before 16.4 sends no `Sec-Fetch-*` at all.

**Browser-enforced versus fakeable.** `Referer`, `Origin` and anything starting `Sec-` are forbidden header names: page script cannot set them ([Fetch Metadata §4.2](https://w3c.github.io/webappsec-fetch-metadata/), read 2026-10-17). That only binds browsers: a client that is not a browser (`curl`) can send any value. No page I read states this sentence for `Sec-Fetch-*`; it follows from the forbidden-name rule, which is about scripts in a browser only. What the browser itself refuses to do (frame-ancestors, below) is the only thing a server does not have to trust.

## 3. CSP `frame-ancestors` for the iframe

All from [CSP3 §6.4.2 and §6.7.2](https://w3c.github.io/webappsec-csp/), read 2026-10-17, and [MDN frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors), read 2026-10-17.

- **Syntax.** `Content-Security-Policy: frame-ancestors <list>` where each item is a scheme (`https:`), a host-source (`https://example.se`, `https://*.example.se`) or `'self'`; or `'none'`. It does not fall back to `default-src`: "a policy that declares `default-src 'none'` will still allow the resource to be embedded by anyone". Missing header means anyone.
- **Scheme.** Write `https://` explicitly. The algorithm: "If expression does not have a scheme-part, and origin's scheme does not scheme-part match url's scheme, return 'Does Not Match'", with `origin` the framed page's own origin, so a scheme-less entry only admits ancestors on the call page's scheme.
- **Wildcard.** The host-part algorithm: for a pattern starting `*.`, take the rest (`.example.se`) and match if the host "ends with remaining". So `*.example.se` matches `www.example.se` and `a.b.example.se` and **does not match `example.se`** (no leading dot). The spec's note: "`*.example.com` host-part matches `www.example.com`". The apex is my reading of the algorithm, not a sentence in the spec, so it needs its own entry. **Seen** (Chromium 141, 2026-10-17): with `https://acme-shop.se https://*.acme-shop.se` the apex, `www.` and a deeper page open the panel and `other-shop.se` is refused.
- **Port.** In the port-part algorithm a missing port matches only the URL's default port; `*` as port matches any (§6.7.2.11, my reading).
- **Path.** The check runs on the ancestor document's origin serialised and parsed as a URL (§6.4.2.1), so there is no real page path to compare. Do not write one. My reading, not stated in the spec as a rule.
- **Whole chain.** The check loops over every ancestor, parent, grandparent and up; one miss gives "Blocked". MDN: "If any ancestor doesn't match, the load is canceled."
- **Not in `<meta>`.** "MUST be ignored when contained in a policy declared via a meta element."
- **Direct visits are not stopped.** Step "If target is not a child navigable, return Allowed". A tab opened on the call URL is never checked.
- **Redirects.** The HTML navigation algorithm runs its CSP and `X-Frame-Options` check on the response the fetch ended with ([HTML browsing the web](https://html.spec.whatwg.org/multipage/browsing-the-web.html), read 2026-10-17), so only the **core's final page** needs the header, and a Django `X-Frame-Options: DENY` on the Portal's 302 should not matter. **Seen** (Chromium 141): a `302` that itself says `X-Frame-Options: DENY` does not block the core page in the frame; a `403` that says it is blocked, so the Portal's `xframe_options_exempt` is needed for its 403 sentence, not for the redirect.
- **Versus `X-Frame-Options`.** The header takes only `DENY` or `SAMEORIGIN`; `ALLOW-FROM` is obsolete and ignored ([MDN XFO](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Frame-Options), read 2026-10-17). When a `frame-ancestors` policy is enforced, `X-Frame-Options` "will be ignored" (CSP3 §6.4.2.2). Django's middleware sets `DENY` on every response unless the header is already set or the view uses `xframe_options_exempt` ([Django clickjacking](https://docs.djangoproject.com/en/stable/ref/clickjacking/), read 2026-10-17).
- **Browsers.** `frame-ancestors`: Chrome 40, Firefox 58, Safari 10, iOS Safari 9.3 (compat data above). Not a concern.

**One domain per Business.** Matching is by origin pattern, not registrable domain, so the stored registrable domain `example.se` becomes two entries: `frame-ancestors https://example.se https://*.example.se`. `http://` and other ports stay out unless the Business asks. Because the domain goes into a response header, validate it at save time as a plain hostname (letters, digits, dots, hyphens, punycode) so a stored value cannot add a directive or break the header; refuse to serve the page if it fails (rule 3).

**Stopping direct visits needs a second check, and it is weaker.** Require `Sec-Fetch-Dest: iframe` on the page request. A paste into a tab sends `document`; a popup sends `document`. A script or `curl` sends `iframe` anyway, and a pre-16.4 iPhone sends nothing, so missing must be answered one way or the other (a choice for Petter). A `Referer` match adds little inside an iframe: `frame-ancestors` already pins the parent in the browser.

## 4. Microphone inside the iframe

- **Secure context.** `getUserMedia` needs HTTPS (or localhost); otherwise `navigator.mediaDevices` is `undefined` ([MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), read 2026-10-17). Both our hosts are HTTPS.
- **Delegation.** The `microphone` default allowlist is `self`; a cross-origin frame is blocked and `getUserMedia` rejects with `NotAllowedError` ([MDN microphone](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy/microphone), read 2026-10-17). MDN: unless the top-level page grants it, "the user will never even be asked". So the loader must create the iframe with `allow="microphone"`. The `allow` attribute can only add a restriction on top of the page's own `Permissions-Policy` header (MDN iframe), so a Business that sends `Permissions-Policy: microphone=()` breaks the button. **Seen** (Chromium 141): the panel looks fine and `getUserMedia` is rejected after Start.
- **Redirect trap.** In `allow` the default value is `'src'`, the origin of the iframe's `src` attribute ([Permissions Policy §6.2](https://w3c.github.io/webappsec-permissions-policy/), read 2026-10-17). MDN: if the frame navigates to another origin, the policy is not applied there unless that origin is listed ([MDN Permissions Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Permissions_Policy), read 2026-10-17). Our Portal `/call/<slug>/` and the core are different origins, so either `src` points at the core directly or `allow` names the core: `allow="microphone https://call.petterannerwall.se"`. **Seen** (Chromium 141): an iframe whose `allow` is `microphone` or missing is refused after the redirect (`NotAllowedError`); `allow="microphone <core origin>"` works.
- **Whose name the visitor sees.** The Permissions spec says most powerful features "grant permission to the top-level origin and delegate access to the requesting document" ([Permissions spec](https://w3c.github.io/permissions/), read 2026-10-17). Chromium's own note says prompts "often appear to be coming from the top-level origin" ([Chromium](https://chromium.org/Home/chromium-security/deprecating-permissions-in-cross-origin-iframes), read 2026-10-17). So expect the Business's site name, not ours. The literal prompt text per browser: **not checked**, and still not after VOI-72: the test driver answered the prompt, so whose name it shows is unseen.
- **Support.** `allow` on iframes: Chrome 60, Firefox 74, Safari 11.1 (iOS mirrors, Chrome Android mirrors). `getUserMedia`: Chrome 53, Firefox 36, Safari 11. The *header* directive `Permissions-Policy: microphone` is Chrome 88 only, Firefox and Safari `false` (compat data), but our snippet only needs the iframe attribute. Whether iOS Safari and Firefox Android honour `allow="microphone"` for a cross-origin frame in practice: **not checked** (no primary source found).
- **Audio start and user gesture.** Web Audio autoplay is gated on *sticky* activation ([MDN user activation](https://developer.mozilla.org/en-US/docs/Web/Security/User_activation), read 2026-10-17). A tap only marks the tapped window, its ancestors and its same-origin descendants ([HTML §6.4.2](https://html.spec.whatwg.org/multipage/interaction.html), read 2026-10-17). So a tap on the launcher in the Business's page does **not** activate our cross-origin frame; the call page needs a tap of its own (a "Start" button inside the frame) before it resumes an `AudioContext`. The `autoplay` policy defaults to `self`, so add `autoplay` to `allow` too ([MDN autoplay](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), read 2026-10-17). WebKit's video-policy post does not mention Web Audio or iframes ([WebKit](https://webkit.org/blog/6784/new-video-policies-for-ios/), read 2026-10-17). WebSocket or `AudioContext` limits inside an iframe on iOS Safari: **not checked**.
- **`/ws` origin check.** A WebSocket handshake carries the origin of the script's document ([Fetch, append a request Origin header](https://fetch.spec.whatwg.org/#append-a-request-origin-header), read 2026-10-17). In the iframe that is the call page itself, so `Origin == Host` should still pass, and it says nothing about the embedder. **Seen** (Chromium 141): the socket opens from inside the panel and the core accepts it.

## 5. The loader script

- **Shape.** `<script async src="https://voice.petterannerwall.se/widget.js" data-business="<slug>"></script>`: `async` fetches in parallel and runs when ready, with no order guarantee ([MDN script](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script), read 2026-10-17). It adds a fixed-position button on click, builds the iframe (`src`, `allow`, `referrerpolicy`), and talks to it by `postMessage`. Both sides must check `event.origin` (and `event.source`) and give an exact `targetOrigin`, never `"*"`: MDN says failing to check "enables cross-site scripting attacks".
- **Customer CSP.** MDN: with `script-src https://example.com/`, a script from another host is "blocked and won't be loaded or executed", and inline scripts are blocked unless allowed by `'unsafe-inline'`, a nonce or a hash ([MDN script-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src), read 2026-10-17). So `script-src` must list the loader's host, or our tag must carry the page's nonce. The iframe needs `frame-src` to allow the core's origin, falling back to `child-src` then `default-src` ([MDN frame-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-src), read 2026-10-17). A strict customer policy such as `default-src 'self'` blocks both and the button silently never appears. **Seen** (Chromium 141): no launcher and no visible message; with only the script allowed the panel is "This content is blocked"; and `frame-src` must name the core as well as the Portal, because the redirect target is checked too. Any fetch from the script to the Portal also needs `connect-src` (same CSP family, **not read**).
- **Only on their page.** The script runs in the Business's origin. Anyone can fetch and run it elsewhere, but the iframe it builds is then refused by `frame-ancestors`.
- **What the Portal sees on the script request.** `Referer` with the page, trimmed to the origin by default. No `Origin`: a plain script load is `no-cors` GET, and the Fetch algorithm adds `Origin` only for CORS requests, WebSockets, or methods other than GET/HEAD (link above). A `crossorigin` attribute on the tag makes it a CORS request; that this adds `Origin` follows from the Fetch rule, the HTML text for the attribute: **not checked**. The Portal could withhold `widget.js` from other `Referer`s, but that is the same deterrent as before and the real stop is the header on the core's page. A `fetch` from `widget.js` to the Portal carries a browser-set `Origin` (earlier note, option b).

## 6. Options for "limit to one domain"

| Option | Stops other sites embedding | Stops direct visits | Stops scripts / `curl` | Business pastes |
|---|---|---|---|---|
| (i) `frame-ancestors` only | Yes, browser-enforced, whole chain | No | No | Loader snippet; must not send `Permissions-Policy: microphone=()`; CSP must allow script and frame |
| (ii) (i) plus `Sec-Fetch-Dest: iframe` (and a `Referer` match) at Portal and core | Yes | Yes in browsers that send the header; pre-16.4 iPhones need a missing-header answer | No: any client can send the headers | Same as (i) |
| (iii) popup with `Referer` check at the Portal | Only where `Referer` survives (`noreferrer`, a no-referrer policy or a privacy setting removes it) | No: a pasted link has no `Referer` (earlier note) | No | A link or tiny script calling `window.open`; no iframe CSP needed |

## 7. Where the checks would sit

The Portal sees the first request (`call_link`) and can read `Referer` and `Sec-Fetch-Dest` there. Only the core's final response can carry `frame-ancestors`, and the core does not know the Business's domain. Options: **(A)** the domain travels in the signed ticket as a field covered by the HMAC (the earlier note describes the current `business_id.kind.expires` form); the core reads it from the verified ticket on the page request and writes the header. This changes the ticket format on both sides and the core's page route, and puts the domain in the URL (not secret). **(B)** the core asks the Portal for the domain by Business at page time through the existing settings port (named in CLAUDE.md; whether it can carry this: **not checked**); no ticket change, one more Portal call per page. **(C)** the Portal serves a thin page that frames the core; then the core's header can be a fixed `frame-ancestors https://voice.petterannerwall.se` and the Portal's page carries the per-Business value (the Portal view needs `xframe_options_exempt` or its own header). Cost: two nested frames on a phone and microphone delegation through both. The core would still be directly openable in a tab, as now. Not designed beyond this.

## Open choices for Petter (questions, not decisions)

1. Iframe panel, or popup? The popup is simpler and needs no customer CSP, but cannot be limited to one domain except by `Referer`.
2. When the page request has no `Sec-Fetch-Dest` (older iPhones, odd clients): refuse or allow?
3. When the site does not match, what does the visitor see? A blocked iframe fires `load`, not `error` (MDN iframe), so the loader cannot tell; the browser shows its own error page ("inline content should indicate to the user the sort of error", HTML navigation text). Do we accept a blank or error box, or add a loader-side timeout and message?
4. What does the Business see when its CSP or `Permissions-Policy` blocks the button? A dashboard check?
5. Does the Business's own dashboard "copy link" stay a plain link that works anywhere?
6. Who edits a Business's domain (also an earlier-note question)?

## What would settle it

A throwaway page on a second domain with the loader, in Safari on an iPhone (before and after 16.4 if possible), Chrome Android and desktop Firefox: read `Sec-Fetch-Dest`, `Referer` and whether the microphone prompt appears and names the Business's site; with the page's `Referrer-Policy: no-referrer`; with a strict CSP; with a wrong domain. This is the "seen to hold" step. Desktop Chromium has been seen (VOI-72, [call-panel-in-browsers.md](call-panel-in-browsers.md)); the phone, Safari and Firefox runs have not.

## Verdict

- Yes for browsers: `frame-ancestors https://example.se https://*.example.se` on the core's page limits embedding to one registrable domain, enforced by the browser across the whole chain, in every current browser.
- It does not stop direct visits or scripts; a `Sec-Fetch-Dest: iframe` check stops casual direct visits in browsers that send it (Safari 16.4 and later) and no script.
- Least work: store one validated domain per Business, carry it in the signed ticket, have the core set the header, and give the iframe `allow="microphone <core origin>; autoplay <core origin>"`, with a Start tap inside the frame; the microphone and iOS audio behaviour must be tried first.
- Questions for Petter: iframe panel or popup; what to show when the domain does not match; what a refused embed looks like to the visitor (see above).
