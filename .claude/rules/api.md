# Request handlers

Every Portal page is a Django view that shows its own state (`portal/accounts/views.py` is the example).

- **Parse, don't validate.** A handler parses its input once, at the boundary, into a typed value (a Django form or the framework's own view). Code past the boundary takes that value and never re-checks raw input.
- **Behind the login by default.** A page for a Business is a `@login_required` view that reads only `request.user`'s Business. A page open to visitors is listed in `OPEN` in `tests/portal/test_routes.py` with its reason.
- **Fail closed.** A page that cannot tell who is asking refuses (the login redirect), never shows.
- **Scripts from our own files only.** Every response carries `SECURE_CSP` (`portal/settings.py`): no inline `<script>` or `on…=` handler, images from the Portal or `data:`, inline styles allowed. A view that needs another policy sets its own header (`logo`) or uses `csp_override` (`call_link`, which drops `frame-ancestors` for the Business's website; `home`, which with `DEMO_BUSINESS_ID` set adds a `script-src` for the Portal's origin and a `frame-src` for the Portal's and the core's, so the demo Call button and its panel load).

## Enforced by

- `tests/portal/test_routes.py`: every route outside `OPEN` sends a visitor to the login.
- One Business never reads another's data: `tests/portal/test_business_settings.py` (a Business edits only its own settings). The settings address for the core (`settings_for_core`) is open in `OPEN` because the shared secret gates it, not a session; its test refuses a missing, wrong or unset secret.
- The Modules page (`modules`, `remove_module`) shows and removes only `request.user`'s Business's Modules; `tests/portal/test_modules_page.py` fails if another Business's Module can be seen, served or removed.
- The Access tokens page (`access_tokens`, `revoke_access_token`) shows and revokes only `request.user`'s Business's tokens and shows a new token's secret once, on the answer to the POST, never in a later view; `tests/portal/test_access_tokens.py` fails if another Business's token can be listed or revoked, or the secret shows again.
- The privacy notice (`privacy`, VOI-245) is open in `OPEN` on purpose: visitors read it before a demo call. It is a static page that reads no Business and no request data; `tests/portal/test_landing.py` holds what it names.
- The logo address (`logo`) is open in `OPEN` on purpose: the core's call page loads it. It is keyed by the hash of the logo's bytes, never a Business's id or call link, and `tests/portal/test_theme.py` fails if an id or call link opens one.
- The public call link (`call_link`) is open in `OPEN` on purpose: `tests/portal/test_call_link.py` shows it takes no Business from the request but its own unguessable slug, only reads, and makes no ticket for a request that does not say it is in a frame, for a Business with no saved website domain, or once the Business's daily budget is spent (test calls apart). The budget refusal sits in `to_core`, the one place a ticket is minted, so every kind `BUDGET_COUNTED` counts is refused from any view (VOI-172); a view that signs a ticket without `to_core` is not refused (not checked: no guard). The Business `DEMO_BUSINESS_ID` names (the landing page's demo, VOI-244) goes through `demo_call` first, which refuses the third call from one address in a day and the 21st demo call of the day before `to_core` mints a `demo` ticket; `tests/portal/test_call_link.py` holds both caps and that the setting unset changes nothing. The Call button script (the static `portal/static/portal/call-button.v1.js`, and `call_button_js` for tags pasted before VOI-135) is open for the same reason: the Business's website loads it, it is the same text for everyone and holds no Business.
- Every page sends the CSP, the logo its own and the call link no `frame-ancestors`: `tests/portal/test_pages.py`; the landing page's demo additions, and none when the setting is unset: `tests/portal/test_landing.py`.
- The test call (`test_call`, a POST behind the login) takes no Business from the request: it mints a ticket for `request.user`'s Business, and `tests/portal/test_test_call.py` fails if the request can name another.
- The calls page (`calls`) shows only `request.user`'s Business's Call records, newest first, with no cost; `tests/portal/test_recent_calls.py` fails if another Business's record, a cost or a call id shows.
- The Call record address (`record_call`, a POST) is open in `OPEN` for the same reason as `settings_for_core`: the shared secret gates it, and `tests/portal/test_call_records.py` refuses a missing, wrong or unset secret before any lookup. The Call log address (`record_call_log`, a POST) is open for the same reason, and the same test, parametrized over both addresses, refuses the same there. Both open through `store_core_report`, which checks the secret, then parses and stores a report from the core; a new report from the core goes through it too (not checked: no guard).
- The agent endpoint (`agent_endpoint`, `POST /mcp/`) is open in `OPEN` on purpose: an Access token gates it, not a session, and a client lists the Commands before it has one. A Command reads only its token's Business; `tests/portal/test_agent_endpoint.py` fails if a Command runs for a token that may not (every Command against every kind of token), if a refusal differs from the answer to a Command that does not exist, or if another Business's call shows.
- The sign-in routes (VOI-119) are open in `OPEN` on purpose: an assistant reads the discovery documents, registers and exchanges codes before anyone is logged in, and the client's own credentials (PKCE, a secret) gate the token and revoke endpoints. The consent page (`oauth_authorize`) is behind the login and grants only `request.user`'s Business; the connection revoke (`revoke_connection`) only the Business's own. `tests/portal/test_oauth.py` fails if a code works twice, without PKCE, with the wrong verifier or for another resource, if a revoked connection's token or refresh token still works, or another Business can revoke one.
- The Pending changes page (`pending_changes`, `approve_change`, `reject_change`) shows and decides only `request.user`'s Business's changes, through `changes.decide`; `tests/portal/test_pending_changes.py` fails if another Business can see or decide one, a GET or a visitor decides one, or a second approval applies. The settings Commands (`read_settings`, `change_settings`, `change_business_details`) use the settings page's form (`settings_form.changed`), and `tests/portal/test_agent_settings.py` fails if the same input is stored or refused differently through the page and a Command. The operator Commands (`list_totals`, `invite_business`) run only for an operator token while `SUPER_ADMIN_EMAIL` names its Account, and `tests/portal/test_agent_operator.py` fails if a Business's token sees or runs one, an unset setting leaves an operator, or a staged invite goes out before the approval or twice. `get_call_button` and `get_test_call_link` take the Business from the token only; the link's ticket comes from `core_address`, shared with `to_core`, with its own kind, `agent_test`, which counts toward the daily budget (the dashboard's `test` stays exempt); `tests/portal/test_agent_call.py` fails if the link opens another page, names another Business or kind, or is given once the budget is spent. The Module Commands (`list_modules`, `check_module`, `add_module`) use the Modules page's form (`module_form.ModuleForm.add`), and `tests/portal/test_agent_modules.py` fails if an add is stored or refused differently, a list asks a Module, a check outlasts its deadline, or another Business's Module answers unlike an unknown one.
- The totals page (`totals`) is behind the login and then the `SUPER_ADMIN_EMAIL` setting, refusing every other Account with 403 (and everyone when it is unset); `tests/portal/test_totals.py` fails if another Account opens it. The Call log pages (`call_logs`, `call_log`) take the same gate through `operator_only`, and `tests/portal/test_call_log_page.py` fails if another Account, its own calls' logs included, opens one.
- The login locks one email from one client address after ten wrong passwords in 15 minutes, and a password reset sends at most five mails per email and address in that window, showing the same sent page after; the address is the last `X-Forwarded-For` entry outside `DEBUG` (meant to be the one the proxy adds; not checked in production, where a proxy in front of Traefik or Docker's ingress would make it one address for everyone), else `REMOTE_ADDR` (`client_address` in `portal/accounts/views.py`). Counts are in process memory, so a restart clears them: `tests/portal/test_accounts.py`.
- A form the CSRF check refuses (a page left open, a login in another tab) gets the Portal's page saying nothing changed, never Django's; a GET of a POST-only address (Test call, Remove) does nothing and goes back to its page: `tests/portal/test_inputs.py` (Remove on the Modules page: `tests/portal/test_modules_page.py`; Revoke on the Access tokens page: `tests/portal/test_access_tokens.py`).
