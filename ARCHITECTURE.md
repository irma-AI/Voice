# Architecture

The map an agent needs before changing structure: the layers, which way dependencies point, and the one interface each cross-cutting concern goes through. Be strict about these boundaries and loose about how code inside a layer is written.

## Layers

Lowest first:

- **Call record** (`voice/record.py`): writes what happened on a call to a JSONL file. Used on the eval Channel only.
- **Barge-in** (`voice/bargein.py`): the Gemini detector settings (`VAD`) and `BargeInRecorder`, which writes a timings-only event for every barge-in. Used by the Agent on every Channel.
- **Portal client** (`voice/portal_client.py`, VOI-168): the one way the core reaches the Portal, and the only module that reads the shared secret (`CORE_SECRET`, `core_secret()`, which the web Channel also takes as the ticket key) or builds a request from the Portal's address (`SETTINGS_URL`; the Settings port reads it too, only to choose its source and name the host). Every request carries the secret as a Bearer token, never follows a redirect, and logs or raises with the Portal's host and the kind of failure only. `get()` tries once and raises `PortalRefused` (fails closed); `post()` tries again for up to a minute and logs each try, and gives up at once on a 4xx other than 408 or 429 (VOI-229). Used by the Settings port, the Call reports port and the web Channel.
- **Call reports port** (`voice/report.py`, VOI-41): `UsageTally` adds up the model's usage reports during a call, and `report_call()` is the one way a finished call leaves a Call record: it prices the call from Google's Cloud Billing Catalog (`voice/cost.py`, VOI-42: dollars, kept in memory for a day, empty with a reason code when it can't be read or matched), builds the record, writes it to the server log as one line, then sends it to the Portal through the Portal client's `post()` in the background and returns, retrying for up to a minute and logging a give-up line if every try fails. The pricing and sending run on the module's own pool (`SENDER`, 4 threads, VOI-128), so records stuck on a down Portal never take the default threads that call starts read settings on; a fifth record waits for a free one. It also sends the call's Call log (VOI-153) the same way, on a pool of its own (`LOG_SENDER`, 4 threads) so a record never waits behind a log: the call's barge-in lines, which a loguru patcher in the module (`keep_barge_in_line`) keeps by call id as they reach the server log, so the stored log is the logged lines and the recorder needs no change; `report_call` takes a call's lines out at its end. It runs only for a call a Portal ticket named (a Business and a kind); the eval Channel names none and leaves no record or Call log. Used by the Agent.
- **Settings port** (`voice/settings.py`): `load_settings()` is the one way the core learns a Business's name, Instructions and languages, read fresh at every call start from the Portal (through the Portal client's `get()`) or from a file; anything unsafe raises `SettingsRefused`. Used by the Agent, and by the call page (`GET /` in `voice/serve.py`) for the Business's name and Theme, which falls back to Voice's own look when it refuses (VOI-87).
- **Actions port** (`voice/modules.py`): `connect_modules()` connects to each of a Business's Modules (MCP servers) at call start and returns the Actions they offer (at most 20, no repeated name), which the Agent hands to the model as its tools and whose connections it closes when the call ends, however it ends; a Module that cannot be used is skipped and logged, never fatal. A local Module (a program the core starts) is used only when `ALLOW_LOCAL_MODULES=1`, which the hosted service never sets; without it a remote Module is used only at an https address that resolves to public addresses only (`address_problem`). Used by the Agent; imports the Settings port for the `Module` type.
- **Agent** (`voice/agent.py`): the prompt, the opening and the disclosure line, the agent's name (`AGENT_NAME`), the Gemini Live service (sent with no speech config, so the server's default voice) and the pipeline, built from one Business's settings and Modules. `run_call(transport)` is the one way a call runs; without safe settings it speaks the refusal and hangs up.
- **Channel**: turns a connection into a Pipecat transport and hands it to `run_call`. `voice/serve.py` is the web Channel (one page and a WebSocket, what `make up` and the Dockerfile run; it waits up to 3 s for the page's first message, its browser facts, before the call starts, and passes on the page's playback gap counts as Pipecat's `InputTransportMessageFrame`; any other text from the page is ignored and logged by kind, once per kind and call); `voice/web.py` is Pipecat's runner, kept for the eval Channel only. A phone Channel will sit beside them.

The **Portal** (`portal/`, ADR 0002) is a second service beside these layers: a Django app with its own Postgres where a Business logs in. It does not import `voice/`, and `voice/` never imports it or reads its database; the core can ask it for a Business's settings over a web address (VOI-24, VOI-25) but does not depend on it: the Portal is one adapter behind the core's settings port (ADR 0002, update 2026-10-14). Inside it: `portal/accounts/models.py` (the database rules) is under `invite.py` and the views, which sit under the URLs; nothing imports upward.

`tests/evals/` is outside the layers. It starts the web Channel on Pipecat's eval transport and imports `DISCLOSURE` from the agent and `HOURS` from the example Module and reads the test Businesses, so each fact keeps one home.

## Dependency direction

Dependencies point down the list: Channel imports Agent, Agent imports Settings port, Actions port, Call reports port, Barge-in and Call record, which import the Portal client, nothing imports upward. Enforced by the `layers` guard from `scripts/checks/layers.json`, which is the one place each layer's files and what it may import are written: `voice/ticket.py` (the call ticket) is a leaf that Call reports, the Agent and the Channel may import, `voice/auth.py` sits with the Channel, and `voice/cost.py` with Call reports. The Portal is its own layer in that file: it imports nothing from `voice/`, and `voice/` imports nothing from it. A layer may import only the layers its `may_import` names, and the guard fails any other import; a new `voice/` file belongs in a layer there, or it is not checked. Not checked: the order inside the Portal (models under `invite.py` and views), and `tests/`.

## Cross-cutting concerns

Each concern has one interface, and code reaches it only through that interface:

- **Secrets and settings**: environment variables, listed in `.env.example`; `GOOGLE_API_KEY` is read in `run_call` and checked up front in `voice/serve.py` and `voice/web.py`; `BILLING_API_KEY` (optional, a key limited to the Cloud Billing API) is read in `voice/report.py` for the price lookup; `CORE_SECRET` only in `voice/portal_client.py`, and `SETTINGS_URL` there and in `voice/settings.py`, which only chooses its source by it.
- **Auth for the web Channel**: `voice.auth.TicketGate`, the one gate in front of every route: only a valid, unexpired Portal call ticket (`voice/ticket.py`) opens the page or the socket; anyone else gets a 403 page with a Swedish sentence, or a closed socket (`voice/serve.py` adds it; it needs `CORE_SECRET`, and `/ws` also accepts only its own site as Origin). `SecurityHeaders` wraps the gate, so every HTTP response, its 403 included, carries HSTS (30 days), `nosniff` and `Referrer-Policy: same-origin` (VOI-132).
- **Ports of the core** (ADR 0002, update 2026-10-14): the core is a hub with lines in, each with one interface and one adapter for now. Channel (web, eval; phone later) and model are Pipecat's own transports and services. Settings (`voice/settings.py`): the Portal's address (`SETTINGS_URL`, `CORE_SECRET`, which `voice/portal_client.py` sends the requests with), which serves only a call that names its Business (the ticket does), or a file (`SETTINGS_FILE`) in the settings shape chosen explicitly for evals, whose Channel names none; none configured is a logged start that refuses calls with a spoken reason, and a Portal that is configured but down refuses too. Actions (`voice/modules.py`): Modules over MCP, named in the settings (`modules`), connected once per call; `modules/example.py` is the example Module (not in the core image). Call reports (VOI-39): the core sends one Call record and one Call log per call to the Portal, never blocking a call (the core's side is `voice/report.py`, VOI-41; the Portal's is below). A new line in is a new adapter behind a port, never a change to the call logic. The Portal and the core depend on the settings shape (VOI-24), never on each other; Modules depend on neither.
- **Portal accounts**: `portal.accounts.models.Account` is the only login (`AUTH_USER_MODEL`); a Business is a `Business` row pointing at its Account. `portal.accounts.invite.invite` is the one way the app creates them and sends an invite, called by the `invite_business` command; there is no sign-up page. Nothing stops other code from creating an Account (not enforced yet). The `offboard_business` command is the one way they leave: it empties the Business's personal data and closes the Account, keeping the rows and Call records by number (VOI-126, `docs/privacy/README.md` § 3a); nothing stops other code from editing them (not enforced).
- **Portal Modules** (VOI-28): `portal.accounts.models.Module` is a name and an address, never a credential (the database refuses an address with a user, password, query or fragment, and an eleventh Module per Business). The page (`/modules/`; the rules in `portal/accounts/modules.py`, the asking in `portal/accounts/probe.py`) adds, removes and lists each Module's Actions by asking it over MCP only when the Business presses Check (VOI-52: a page view never connects to a Module); `Business.modules_to_serve` is the one place that decides which Modules the core is told about. `ALLOW_LOCAL_MODULES` is read by `portal/settings.py` and by the core: the Portal's copy of the address rule and the core's are held together by `tests/test_modules.py`.
- **Test call** (VOI-26): the Portal's dashboard button (`POST /test-call/`, logged-in Business only) redirects the browser to the core's call page (`CORE_URL`) with a ticket: the Business's id, the kind of call (`test`) and an expiry signed with `CORE_SECRET` (`portal/accounts/ticket.py` signs, `voice/ticket.py` checks, `tests/portal/test_test_call.py` holds the two together). The core opens the page and the socket for a valid ticket and reads that Business's settings from the Portal; a visitor without a valid ticket is refused (VOI-45).
- **Call link** (VOI-29): a Business's public call link is `GET /call/<call_slug>/` on the Portal (open to anyone; the slug is unguessable and unique in the database, `Business.call_slug`), which redirects to the core's call page with a ticket for that Business, exactly like the test call but with the kind `call_link` and the Business's saved website domain (`to_core` in `portal/accounts/views.py`). It does so only when the request says it is loading a frame (`Sec-Fetch-Dest: iframe`, VOI-73) and the Business has saved a domain (VOI-71); every other request, a tab, a pasted link, a script's fetch or a browser that sends no such header (Safari before 16.4), gets a 403 and the English sentence "This call can't be opened from here. Start it from the company's own website.", logged with the Business id, and no ticket. The route is exempt from Django's own `X-Frame-Options: DENY` (`xframe_options_exempt`); every other Portal page keeps it. A Business has one call open at a time (VOI-59: `OneCallPerBusiness` in `voice/serve.py` refuses the socket of a second one, in the core's memory; `tests/test_serve.py` holds the rule); each day (on `TIME_ZONE`) a Business's Call link calls spend at most `Business.daily_budget_usd` (default $10, set by the operator only; the database refuses a negative one): once today's priced records, plus the seconds of unpriced ones (and ones priced at $0, a call with no usage report) at the rate Google charged the Business's priced calls so far, never below `WORST_CASE_USD_PER_SECOND` (Google's official rate for a full 10-minute call, $0.001875 a second, logged with the Business id; VOI-216, fail closed), reach it, `to_core` (where every ticket is minted, VOI-172) refuses a kind `BUDGET_COUNTED` counts with the sentence "Something went wrong. We can't take calls right now.", logged with the Business id, and no ticket (VOI-123; `spent_today` in `portal/accounts/views.py`). When the core's live price lookup fails, it prices the call's tokens from the stored copy of Google's official rates (`voice/prices.json`, dated by its `as_of`, which becomes the record's `price_date`; VOI-216), so only a call with no tokens reaches the Portal unpriced. Test calls neither count nor are refused, a call still open is not counted, so one call may run over, and each call is cut at the core's 10 minutes. A budget of 0 refuses every Call link call: the off switch. A ticket already minted still opens calls until it expires (10 minutes), so the overrun is bounded by one ticket's worth of calls (`DECISIONS.md`). `tests/portal/test_call_link.py` holds it.
- **Call button** (VOI-73, replacing VOI-31's plain link): the dashboard shows a script tag, `<script async src=<Portal>/static/portal/call-button.v1.js?business=<call slug> data-core=<core origin> data-fill=<accent> data-ink=<its text> integrity=sha384-<hash> crossorigin=anonymous>`, only once a website domain is saved (VOI-135). The script is a static file, `portal/static/portal/call-button.v1.js`, served by WhiteNoise to anyone with `Access-Control-Allow-Origin: *` (the CORS a cross-origin integrity check needs); the tag carries the core's origin and the named Business's adjusted accent and its text (Voice's Deep sea and Foam for no accent; `call_button_tag` in `portal/accounts/views.py`), and the hash of the file's bytes, so a browser runs only that exact file. `make generate` writes the hash to `portal/call-button.v1.integrity` and `make generate-check` fails when the file changed without it; since every pasted tag names the hash, a changed script is a new file (`call-button.v2.js`, with the dashboard's tag and the old route's `CALL_BUTTON_FILE` pointing at it), never an edit to v1: the `frozen-paths` guard fails a PR that touches the file or its hash (the `frozen` list in `scripts/low-risk-paths.json`, read from the base branch), and `.gitattributes` keeps a checkout from rewriting their line endings. A tag pasted before VOI-135, `<script async src=<Portal>/call-button.js?business=<call slug>>`, keeps working: that route (`call_button_js`) writes the three attributes onto the tag in front of the same file (Voice's look for an unknown slug, or a VOI-73 tag that names the Business in `data-business`); a tag without the attributes draws nothing and says so in the console. Seen in Chromium on a local stand-in page on another origin (2026-10-18, VOI-135): the new tag mounts its launcher in the Business's accent and opens the panel, a tag with a wrong hash is refused by the browser and mounts nothing, and the old tag still mounts. It adds a launcher to the page, inside a closed shadow root styled by a constructed stylesheet so host CSS, a strict `style-src` and Trusted Types leave it alone (VOI-89, seen in headless Chromium on a local test site); pressing it adds an iframe on the Portal's Call link with `allow="microphone <core origin>; autoplay <core origin>"` (the link redirects to the core, and an iframe grants those only to the origin it names), and pressing it again, or Escape, removes the iframe, which ends the call. The page and the panel send each other no messages. The call page inside keeps its own Start button, because a tap on the launcher does not activate a cross-origin frame. Which site may do this is the core's `frame-ancestors` (see Website domain), enforced by the browser; the `Sec-Fetch-Dest` check above only keeps casual visits out, since a script or `curl` can send that header and then open the core's page in a tab (not enforced). Seen in headless Chromium on a local stand-in (VOI-89): `frame-ancestors` refusing another site's iframe (the panel then shows the browser's blank error page). Seen in desktop Chromium 141 (VOI-72, `docs/research/call-panel-in-browsers.md`): the panel on the saved domain, its subdomains and deeper pages, another site and a chain with another site refused, a tab refused at the Portal, the microphone after the redirect, the socket from inside the frame. A site whose own Content-Security-Policy does not allow the Portal's script and the Portal's and the core's frames, or whose `Permissions-Policy` blocks the microphone, gets no button or a blocked panel. Seen on one iPhone (2026-10-18): the microphone prompt showing the framing site's name and audio after the Start tap, from a test page on the same site as the Portal. Not seen: Android, an iPhone before iOS 16.4, Firefox, desktop Safari, a test page on another domain. The script runs with full privileges on every Business's site; the hash in the tag means a compromised Portal cannot change what a pasted tag runs, only what a tag pasted after the compromise names, and the old route's script stays the Portal's to change (a tag pasted before VOI-135 has no hash). `tests/portal/test_call_link.py` holds the route, the file, its hash and the snippet.
- **Website domain** (VOI-70): `Business.website_domain` is the registrable domain of the Business's own website, empty for none, saved from the settings page (`SettingsForm`) and shown on the dashboard. `portal/accounts/domain.py` is the one place a typed address or host becomes that domain (`publicsuffixlist`'s bundled list, private section counted, no network); the database refuses a stored value that is not empty or a plain lower-case punycode domain. The settings contract does not carry it; a call link's ticket does (VOI-71): `<business id>.<kind>.<expiry>.<domain>.<signature>`, empty domain for a test call. The core refuses a call link ticket whose domain is not a plain hostname, and its call page sends `Content-Security-Policy: frame-ancestors https://<domain> https://*.<domain>` (for a test call `frame-ancestors 'none'`), so the browser lets only that site frame the page (`frame_ancestors` in `voice/ticket.py`; the pattern is written there and in `domain.py`, and `tests/portal/test_call_link.py` fails naming the side to edit when they differ). A plain tab can still open the core's page with a ticket in hand; the Portal hands one out only to a request in a frame (VOI-73, Call link). Not enforced yet: the database and the core accept any plain hostname, so a bare public suffix (`github.io`) put in by the shell, not the settings form, would let every site on it frame the page; no route stores one today. `tests/portal/test_website_domain.py` holds it.
- **Business settings shape**: `contract/business-settings.schema.json` is the one definition of what the Portal tells the core (`modules` is filled from the Portal's Modules page, `Business.modules_to_serve`). The Portal serves it from `Business.as_settings` at `GET /api/settings/<business id>/`, which wants the shared secret (`CORE_SECRET`) as a Bearer token; `tests/portal/test_settings_contract.py` fails when the model, the form or the schema drifts and names the side to edit. The AI notice is not in it.
- **Theme** (VOI-83): a Business's optional logo and accent colour (`portal/accounts/theme.py`), saved on the settings page. The database refuses a logo over 256 KB, one whose bytes do not start like a PNG, WebP or JPEG (the type is read from the bytes, never the name; no SVG), a `logo_key` that is not the SHA-256 of the logo (`Business.set_logo` is the one way they change together), and an accent that is not `#` and six lower-case hex digits. The logo is served publicly at `GET /logo/<logo_key>/` (`logo` in `portal/accounts/views.py`), an address that names no Business, with its type, `nosniff` and a year's immutable cache. The contract's optional `theme` carries the accent already adjusted for WCAG 2.2 AA with the text it carries (`theme.on_accent`, one copy, in the Portal) and the logo's address; the core's settings port reads it into `Settings.theme`. `tests/portal/test_theme.py` holds it.
- **Call records** (VOI-40): `contract/call-record.schema.json` is the one definition of a Call record (ids, kind, UTC start, length, token counts, dollar cost or empty with a reason; numbers, codes and times only, never words or audio). The Portal stores it at `POST /api/calls/` (`record_call`, shared secret as a Bearer token, 401 before any lookup like the settings address): a malformed record or an unknown Business is refused, a repeated `call_id` answers success and stores nothing more. `CallRecord` is final: a trigger (migration 0007) refuses UPDATE and DELETE for every role, and the Business it points at cannot be deleted. `tests/portal/test_call_records.py` holds the schema, the Portal and the database together. The core sends it (VOI-41): `voice/report.py` logs the record first, then posts it to `SETTINGS_URL`'s `/api/calls/` with `CORE_SECRET` through `voice/portal_client.py`, the kind coming from the call ticket (`tests/test_report.py` holds the record and its delivery to a stand-in Portal, `tests/test_ticket.py` the kinds against the contract).
- **Call logs** (VOI-153): `contract/call-log.schema.json` is the one definition of a Call log (the call's id, Business, kind and UTC start, and its barge-in events as logged). The Portal stores it at `POST /api/call-logs/` (`record_call_log`), gated and answered like `record_call`, in the `CallLog` table beside the Call records. The database (migration 0020) refuses UPDATE for every role, DELETE before `accounts_call_log_expires_at` (30 days after the call's start; the job that deletes after it is VOI-157), and an event field outside `accounts_call_log_fields()` or a value that is not a number, true or false or a short code (a level trace: at most 20 numbers, migration 0023; the browser facts and gap count, 0024), and a start more than an hour in the future (it would outlive its 30 days); the Business it points at cannot be deleted. `tests/portal/test_call_logs.py` holds the schema, the Portal, the database and the security rule's field list together; `tests/test_report.py` the core's log and its delivery to a stand-in Portal. The operator reads them at `GET /logs/` (VOI-158: the newest 100, each with its length from the end event, barge-ins and barge-ins with no Caller's words after), and one log's events as a timeline at `/logs/<call id>/`, whose Copy as text button copies its lines as the server log wrote them (VOI-223); gated like Totals (`operator_only`), `tests/portal/test_call_log_page.py`.
- **Recent calls** (VOI-43): a logged-in Business sees its own latest Call records at `GET /calls/` (`calls` in `portal/accounts/views.py`): start, length and kind, newest first, no cost and no call id. Times show on `TIME_ZONE` (an environment setting, default UTC; the Portal refuses to start on a name that is not a time zone); stored times stay UTC. `tests/portal/test_recent_calls.py` holds it.
- **Totals** (VOI-44): `GET /totals/` (`totals` in `portal/accounts/views.py`) lists every Business per month (call start on `TIME_ZONE`), test calls and Call link calls apart, each with calls, minutes, dollars and a count of calls without a cost. Only the Account whose email is the `SUPER_ADMIN_EMAIL` setting may open it (unset: nobody); anyone else logged in gets 403, a visitor the login. `tests/portal/test_totals.py` holds it.
- **Access tokens** (VOI-111, ADR 0003): a Business makes and revokes `AccessToken`s at `/tokens/` (`access_tokens`, `revoke_access_token` in `portal/accounts/views.py`), read-only or full, with a label. `AccessToken.make` and `AccessToken.revoke` are the only code that makes or revokes one, and the page is the only caller (not enforced: nothing stops other code calling them, setting `revoked_at` to the statement's time, or making a token with `is_operator` for a non-operator; the page alone decides it, from `sees_totals`). The secret (`voice_` and 256 random bits, `portal/accounts/tokens.py`) is on the page that answers the POST and nowhere after; the database holds its SHA-256, and refuses a scope other than read or full, a hash that is not a lower-case SHA-256 hex, a repeated hash and a blank label. A trigger (migration 0014, widened by 0022) lets only `last_used_at`, a first `revoked_at` and `offboard_business`'s renaming of a revoked token's label to `Token <id>` change, and takes only the database's own clock as the revoked time; another (0021) refuses every delete, a Business's cascade included. A token made by the Account whose email is `SUPER_ADMIN_EMAIL` is marked operator for good (`is_operator`). The agent endpoint reads them (below) and sets `last_used_at` on each request. `tests/portal/test_access_tokens.py` holds it.
- **Agent endpoint** (VOI-112, ADR 0003): `POST /mcp/` (`endpoint` in `portal/accounts/agent.py`) serves a Business's Commands over MCP, both protocol eras (2025-11-25 and 2026-07-28), through the official SDK (`MCPServer`) inside a Django view (`django-stateless-mcp`, pinned). Every Command is in that module and is added through `command` (a test fails for a tool added any other way), which checks the caller's token against the Command's entry in `COMMANDS` (read, write, operator read, operator write; no entry is refused), stops each of its database statements after 5 s (Postgres `statement_timeout`, `COMMAND_TIMEOUT_MS`; nothing else in a Command is timed) and leaves a `CommandRecord` (the Command's name, token, the database's time and how it ended, never its values); a trigger (migration 0025) refuses UPDATE and DELETE of a record for every role. A refused Command gets the SDK's own "Unknown tool" answer, so a refusal does not tell a hidden Command exists. `tools/list` follows the token (`follows_the_token`, on the SDK's provisional middleware): with no token it shows the Business's Commands, never the operator's. A wrong or revoked token gets a 401 on any request, and no token a 401 on anything but the handshake, discovery and `tools/list`, with `WWW-Authenticate` for a client's Connect flow (VOI-119). An `Origin` other than `PORTAL_URL` gets 403, and more than `AT_ONCE` (2) requests at once a 503 with `Retry-After`, so the requests it serves keep at least half of gunicorn's 4 threads for the core's settings requests at call start (a client that sends its body slowly holds a thread before any view runs, which no Portal page bounds: not checked behind Traefik). A refusal is made in the SDK's middleware before the SDK reads the arguments, so an argument's error never tells a hidden Command exists, and an argument the schema does not name is refused; the token is read again, without a lock, in the Command's transaction just before it runs, so a revoke refuses every later Command (one already past that read finishes), and the record of a done Command is written in the same transaction. A Command record's time is the database's clock (migration 0025). Commands: `list_recent_calls` (the Business's newest 20 Call records, start, length and kind; no cost, no call id) and `remove_module` (staged, below). `tests/portal/test_agent_endpoint.py` holds every Command against every kind of token.
- **Pending changes** (VOI-239): a destructive Command does not act. It calls `changes.stage` (`portal/accounts/changes.py`), which stores a `PendingChange` (the token, a kind from `CHANGE_KINDS`, its target and the database's time) and answers `staged: true` with a preview, a `risk_level` and `next`; its Command record says `staged`. The Business approves or rejects it at `/changes/` (`pending_changes`, `decide_change`), and only `changes.decide` decides one, for its own Business only: an approval applies it in the same transaction through the Portal page's own function (`changes._apply`, a closed match on the kind: `remove_module` calls `Module.remove`). Triggers (migration 0026) take only the database's clock, refuse a second decision, an approval 7 days after staging (`changes.WAITS`), any other change and any delete. Stage, approval and rejection go to the `portal.audit` log, ids only. `tests/portal/test_pending_changes.py` holds it.
- **Portal settings**: `portal/settings.py`, from environment variables listed in `.env.example`; outside a local run (`DEBUG` off) a missing value stops the Portal.
- **Logging**: Pipecat's loguru logger; `run_call` caps it at INFO so transcripts stay out of logs (`.claude/rules/security.md`).
- **Barge-in log**: `BargeInRecorder`, the only writer of the events `config`, `bot_speech`, `barge_in`, `levels`, `caller_words`, `resumed` and `end`, one JSON line each with the call id and seconds since the call began (VOI-154). A `barge_in` names what cut the agent off (`src`: `gemini` when the model's signal comes upstream, `pipecat` when an interruption from before the recorder cuts the agent off more than a second after the last cut, since Pipecat's turn handling interrupts on every Caller transcript) and the echo signature (`echo_corr`, `echo_lag_ms`: how closely the Caller's sound envelope followed the agent's in the half second before, and at what delay); `levels` traces both sides in 100 ms steps from half a second before the cut to half a second after (shorter when the next cut or the end comes first); `caller_words` scores how many of the first word pairs heard were the agent's own (`similarity`, compared in memory, no word written); `end` sums up `barge_ins`, `no_words` and `cut_share`. On the web Channel (VOI-159) `config` also holds what the call page says the browser applied (the microphone's echo cancelling, noise suppression and auto gain, whether the echo-cancelling loopback route was set up, fell back, or was skipped (iOS, VOI-222), the audio context's rate and latencies, the browser family and OS major version from fixed lists) and `page_facts` (`sent`, `not_sent` or `refused`), and `end` the page's `playback_gaps` count, only when the facts were sent; `voice/serve.py` checks every field, the page's JavaScript is not tested. The recorder's `output_side` sits right after the output transport, where it hears the agent's audio as played and its words. In production a line goes to the server log at INFO, prefixed `barge-in`; on the eval Channel the same line also lands in the call's JSONL file. A production line may hold only the fields in `.claude/rules/security.md`. At call end the Call reports port sends a ticketed call's lines to the Portal as its Call log.
- **Call record**: `CallRecorder`, passed to `run_call` as `record_to`, set only on the eval transport. It also writes a `tool_call` event (the Action's name, never its arguments), which the `module_hours` Scenario checks.
- **AI disclosure**: `DISCLOSURE` in `voice/agent.py`.
- **Business Instructions**: not in the code; they come through the settings port. The eval Channel serves `tests/evals/business.json` (the test Business, a synthetic one), which `tests/evals/run.py` names as `SETTINGS_FILE` for every Scenario but `module_hours`, which gets `tests/evals/business_module.json` (a Business whose Module is `modules/example.py`), and `module_injection`, which gets `tests/evals/business_hostile.json` (the same Business with `modules/example_hostile.py`, whose result carries an instruction), and `module_web`, which gets `tests/evals/business_web.json` (the same Business with `modules/example_web.py`, a web-search Action), all with `ALLOW_LOCAL_MODULES=1`.

No feature flags exist yet; the barge-in log, kept as Call logs, is the only telemetry.
