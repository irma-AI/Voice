# Architecture

The map an agent needs before changing structure: the layers, which way dependencies point, and the one interface each cross-cutting concern goes through. Be strict about these boundaries and loose about how code inside a layer is written.

## Layers

Lowest first:

- **Call record** (`voice/record.py`): writes what happened on a call to a JSONL file. Used on the eval Channel only.
- **Barge-in** (`voice/bargein.py`): the Gemini detector settings (`VAD`) and `BargeInRecorder`, which writes a timings-only event for every barge-in. Used by the Agent on every Channel.
- **Settings port** (`voice/settings.py`): `load_settings()` is the one way the core learns a Business's name, facts and languages, read fresh at every call start from the Portal or from a file; anything unsafe raises `SettingsRefused`. Used by the Agent.
- **Actions port** (`voice/modules.py`): `connect_modules()` connects to each of a Business's Modules (MCP servers) at call start and returns the Actions they offer (at most 20, no repeated name), which the Agent hands to the model as its tools and whose connections it closes when the call ends, however it ends; a Module that cannot be used is skipped and logged, never fatal. A local Module (a program the core starts) is used only when `ALLOW_LOCAL_MODULES=1`, which the hosted service never sets; without it a remote Module is used only at an https address that resolves to public addresses only (`address_problem`). Used by the Agent; imports the Settings port for the `Module` type.
- **Agent** (`voice/agent.py`): the prompt, the disclosure line, the Gemini Live service and the pipeline, built from one Business's settings and Modules. `run_call(transport)` is the one way a call runs; without safe settings it speaks the refusal and hangs up.
- **Channel**: turns a connection into a Pipecat transport and hands it to `run_call`. `voice/serve.py` is the web Channel (one page and a WebSocket, what `make up` and the Dockerfile run); `voice/web.py` is Pipecat's runner, kept for the eval Channel only. A phone Channel will sit beside them.

The **Portal** (`portal/`, ADR 0002) is a second service beside these layers: a Django app with its own Postgres where a Business logs in. It does not import `voice/`, and `voice/` never imports it or reads its database; the core can ask it for a Business's settings over a web address (VOI-24, VOI-25) but does not depend on it: the Portal is one adapter behind the core's settings port (ADR 0002, update 2026-10-14). Inside it: `portal/accounts/models.py` (the database rules) is under `invite.py` and the views, which sit under the URLs; nothing imports upward.

`tests/evals/` is outside the layers. It starts the web Channel on Pipecat's eval transport and imports `DISCLOSURE` from the agent and `HOURS` from the example Module and reads the test Businesses, so each fact keeps one home.

## Dependency direction

Dependencies point down the list: Channel imports Agent, Agent imports Settings port, Actions port, Barge-in and Call record, nothing imports upward. Not enforced yet: `scripts/checks/layers.json` does not exist, so the `layers` guard is off (`DECISIONS.md`). When it exists, a layer may import only the layers its `may_import` names, and the guard fails any other import.

## Cross-cutting concerns

Each concern has one interface, and code reaches it only through that interface:

- **Secrets and settings**: environment variables, listed in `.env.example`; `GOOGLE_API_KEY` is read in `run_call` and checked up front in `voice/serve.py` and `voice/web.py`.
- **Auth for the web Channel**: `voice.auth.BasicAuth`, the one login in front of every route: the Basic login, or the cookie the page sets after it, because browsers don't reliably send the Basic login on a WebSocket (`voice/serve.py` adds it; it needs `VOICE_PASSWORD`, and `/ws` also accepts only its own site as Origin).
- **Ports of the core** (ADR 0002, update 2026-10-14): the core is a hub with lines in, each with one interface and one adapter for now. Channel (web, eval; phone later) and model are Pipecat's own transports and services. Settings (`voice/settings.py`): the Portal's address (`SETTINGS_URL`, `CORE_SECRET`, `BUSINESS_ID`), or a file (`SETTINGS_FILE`) in the settings shape chosen explicitly for evals and local runs; none configured is a logged start that refuses calls with a spoken reason, and a Portal that is configured but down refuses too. Actions (`voice/modules.py`): Modules over MCP, named in the settings (`modules`), connected once per call; `modules/example.py` is the example Module (not in the core image). Call reports (VOI-30): to the Portal, never blocking a call. A new line in is a new adapter behind a port, never a change to the call logic. The Portal and the core depend on the settings shape (VOI-24), never on each other; Modules depend on neither.
- **Portal accounts**: `portal.accounts.models.Account` is the only login (`AUTH_USER_MODEL`); a Business is a `Business` row pointing at its Account. `portal.accounts.invite.invite` is the one way the app creates them and sends an invite, called by the `invite_business` command; there is no sign-up page. Nothing stops other code from creating an Account (not enforced yet).
- **Portal Modules** (VOI-28): `portal.accounts.models.Module` is a name and an address, never a credential (the database refuses an address with a user, password, query or fragment, and an eleventh Module per Business). The page (`/modules/`; the rules in `portal/accounts/modules.py`, the asking in `portal/accounts/probe.py`) adds, removes and lists each Module's Actions by asking it over MCP; `Business.modules_to_serve` is the one place that decides which Modules the core is told about. `ALLOW_LOCAL_MODULES` is read by `portal/settings.py` and by the core: the Portal's copy of the address rule and the core's are held together by `tests/test_modules.py`.
- **Test call** (VOI-26): the Portal's dashboard button (`POST /test-call/`, logged-in Business only) redirects the browser to the core's call page (`CORE_URL`) with a ticket: the Business's id and an expiry signed with `CORE_SECRET` (`portal/accounts/ticket.py` signs, `voice/ticket.py` checks, `tests/portal/test_test_call.py` holds the two together). The core opens the page and the socket for a valid ticket and reads that Business's settings from the Portal; a ticket that fails refuses the call, and the shared login without a ticket still serves `BUSINESS_ID`.
- **Call link** (VOI-29): a Business's public call link is `GET /call/<call_slug>/` on the Portal (open to anyone; the slug is unguessable and unique in the database, `Business.call_slug`), which redirects to the core's call page with a ticket for that Business, exactly like the test call (`to_core` in `portal/accounts/views.py`). There are no call limits or off switch yet (`DECISIONS.md`): anyone with the link can start a call, up to the core's 10-minute cap each. `tests/portal/test_call_link.py` holds it.
- **Call button** (VOI-31): the dashboard shows a snippet, a plain `<a href=<call link> target="_blank">` with the button text, for the Business to paste into its own website. It needs no script, no new route and no core change; it is only the call link, so it works from any website (Petter dropped a list of allowed websites, `DECISIONS.md`). `tests/portal/test_call_link.py` holds it.
- **Business settings shape**: `contract/business-settings.schema.json` is the one definition of what the Portal tells the core (`modules` is filled from the Portal's Modules page, `Business.modules_to_serve`). The Portal serves it from `Business.as_settings` at `GET /api/settings/<business id>/`, which wants the shared secret (`CORE_SECRET`) as a Bearer token; `tests/portal/test_settings_contract.py` fails when the model, the form or the schema drifts and names the side to edit. The AI notice is not in it.
- **Portal settings**: `portal/settings.py`, from environment variables listed in `.env.example`; outside a local run (`DEBUG` off) a missing value stops the Portal.
- **Logging**: Pipecat's loguru logger; `run_call` caps it at INFO so transcripts stay out of logs (`.claude/rules/security.md`).
- **Barge-in log**: `BargeInRecorder`, the only writer of the events `config`, `bot_speech`, `barge_in`, `caller_words`, `resumed` and `end`, one JSON line each with the call id and seconds since the call began. In production a line goes to the server log at INFO, prefixed `barge-in`; on the eval Channel the same line also lands in the call's JSONL file. A production line may hold only the fields in `.claude/rules/security.md`.
- **Call record**: `CallRecorder`, passed to `run_call` as `record_to`, set only on the eval transport. It also writes a `tool_call` event (the Action's name, never its arguments), which the `module_hours` Scenario checks.
- **AI disclosure**: `DISCLOSURE` in `voice/agent.py`.
- **Business facts**: not in the code; they come through the settings port. The eval Channel serves `tests/evals/business.json` (the test Business, a synthetic one), which `tests/evals/run.py` names as `SETTINGS_FILE` for every Scenario but `module_hours`, which gets `tests/evals/business_module.json` (a Business whose Module is `modules/example.py`) and `ALLOW_LOCAL_MODULES=1`.

No feature flags exist yet; the barge-in log is the only telemetry.
